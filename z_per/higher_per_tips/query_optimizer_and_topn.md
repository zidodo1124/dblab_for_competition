# 查询计划优化

本文记录本轮已落地的通用性能优化。所有优化保持 SQL 原有语义，不依赖固定表名、字段名或评测 SQL 文本。

## 1. 统一 SELECT 优化计划与等值谓词传递

### 优化点

普通 SELECT 以前没有复用 EXPLAIN ANALYZE 使用的完整优化计划路径，导致谓词下推、列裁剪、连接顺序选择和内表索引探测不能稳定用于真实查询。

### 优化方法

- 将普通 SELECT、EXPLAIN ANALYZE 与 UNION 分支统一到 `generate_optimized_select_plan`。
- 多表查询在扫描端下推本表过滤条件和仅需的列；连接内表可被提升为索引扫描。
- 在等值连接图中传播常量条件。例如 `A.x = B.y AND B.y = 1` 会推导出 `A.x = 1`，让 A 上的复合索引可以在连接前使用完整前缀。
- 连接顺序估算不再为每张参与表执行一次完整顺序扫描，而是使用文件页数与每页记录容量作为低成本基数代理。

### 优化原因

TPC-C 包含大量主键和复合键查询。常量经连接条件传递后，复合索引的前导列能更早绑定，减少宽行扫描、连接中间记录和不必要的索引范围访问。规划阶段避免全表扫描也防止大表查询在生成计划时产生线性额外开销。

### 验证

- `cmake --build build --target rmdb -j2` 已通过。
- `tools/profile_rmdb.sh --mode inlj --rows 3000 --build-dir build --no-build --profiler timing` 已确认索引嵌套循环计划生效；3000 行连接的建索引后耗时为 0.0177 秒，建索引前为 3.7865 秒。该数据用于确认计划路径，不应将全部差异归因于本优化。

## 后续验证要求

每轮性能优化收敛后，必须重新执行 Phase 2 加载、Phase 3 一致性和崩溃恢复验证；最终以完整 TPC-C 负载的正确性检查与 tpmC 结果作为是否保留优化的依据。
